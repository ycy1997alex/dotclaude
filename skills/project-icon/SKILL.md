# Generating a project's app icon

`ui-project` says the `.ico` must be multi-resolution and that a missing one is a question for the user, not something to invent silently. This file is what happens after the user says yes: how the icon gets drawn, where the script lives, and how to tell whether it worked.

Ask before generating. An icon is a visual identity decision; do not produce one unprompted.

## 1. The icon is generated by a script in the repo, not a one-off

Write `tools/make_icon.py` and commit it. Never hand-place a `.ico` that no script can reproduce — the next person who wants a colour changed has nothing to edit, and there is no record of why the shapes are what they are.

The script's docstring carries three things: the exact interpreter path that runs it, one line on what the image depicts, and any shape that was tried and rejected. That last one is the part people delete; keep it. It is the only thing stopping the next session from re-proposing the design that already failed at 16px.

```python
r"""產生 app.ico。

要換圖示就改這裡再重跑一次：
    C:\path\to\env\python.exe tools\make_icon.py

在 1024px 畫布上畫、再降採樣，形狀刻意做粗，縮到 16px 時才不會糊成一團。
<one line: what the picture is>
<one line per rejected shape, and why>
"""
```

Requires Pillow. It is a build-time dependency like PyInstaller — keep it out of `requirements.txt` unless the app itself imports it.

## 2. Draw big, downsample once

Draw on a 1024px square and let LANCZOS produce every size. Drawing each size by hand produces six icons that disagree with each other.

```python
CANVAS = 1024
ICO_SIZES = [16, 32, 48, 64, 128, 256]

master = draw_icon()                       # RGBA, transparent outside the tile
frames = [master.resize((s, s), Image.Resampling.LANCZOS) for s in ICO_SIZES]
frames[-1].save(OUT, format="ICO", sizes=[(s, s) for s in ICO_SIZES],
                append_images=frames[:-1])
```

`ICO_SIZES` must contain at least 16, 32, 48 and 256 (`ui-project`). Save from the largest frame with the rest in `append_images`; passing only `sizes=` to a small image gives an upscaled, soft result.

## 3. What survives at 16px, and what does not

The whole design is constrained by one number: at 16px, a 1024px canvas is scaled by 1/64. A 100px gap becomes 1.5px. That is the entire brief.

- **Two or three shapes, no more.** Every additional element costs about 2px of separation that is not available.
- **Strokes at least 60px** on the 1024 canvas (≈1px at 16). Thin lines vanish; hairlines alias into grey mush.
- **Gaps between separate shapes at least 100px.** Below that they merge into one blob and the icon reads as a smear. This is the single most common failure, and it is invisible at 256px.
- **A filled rounded-square tile behind everything**, `margin ≈ 40`, `radius ≈ 170`. It gives the icon an outline on any background and stops the shapes touching the edge.
- **Two colours plus white**, at high contrast against the tile. Small icons carry no gradient, no shadow, no inner detail.
- **No text.** Not even one letter — a glyph at 16px is 4 or 5 pixels tall.

Take the colours from the project's actual UI theme rather than picking them, so the icon and the running app agree. For ttkbootstrap:

```python
from ttkbootstrap.themes.standard import STANDARD_THEMES
print(STANDARD_THEMES["litera"]["colors"])   # primary / success / info / warning / danger
```

`primary` for the tile and `success` (or `warning`) for the one accent shape is a reliable default.

## 4. Draw what the project does, not what its category is

The icon should be recognisable as *this* app in a taskbar of twenty. A generic mark for the category is worth very little: the second BLE tool on the machine gets the same one.

Two traps worth naming, because both look fine while drawing and fail on the desktop:

- **Accidental resemblance to a system icon.** Centred concentric arcs are Wi-Fi. A gear is Settings. A folder is Explorer. Check the 16px render against what the OS already ships before committing to a shape — an off-centre or one-sided variant usually fixes it while keeping the meaning.
- **Trademarked marks.** The Bluetooth rune, USB trident, platform logos, and company wordmarks are not free to embed in an app icon. Draw the concept (a device broadcasting) rather than the brand's symbol for it.

## 5. Verification — render it small and look at it

`print(im.ico.sizes())` proves the frames exist. It says nothing about whether the icon is legible, which is the only thing that ever goes wrong. Render a contact sheet and read it back yourself — for an image, "verification is never self-verification" (global: Delegation to Subagents) means eyes on the pixels, not an exit code:

```
python scripts/preview_ico.py path\to\app.ico --out preview.png
```

It writes 256 / 48 / 32 / 16 side by side, each nearest-neighbour upscaled so the actual pixel grid is visible. Open it and check:

1. At 16px the shapes are still separate — no two elements have merged.
2. The silhouette at 16px is the same silhouette as at 256px.
3. It is not mistakable for a Wi-Fi, gear, folder, or shield icon.

If any of the three fails, change the drawing and re-run. Do not proceed to packaging with a 16px frame that is a blob; every place Windows shows a small icon (Explorer details view, Alt-Tab, taskbar at 100% scaling) will show that blob.

Delete the preview PNG afterwards unless the user asked for it.

## 6. Handoff

Once the `.ico` passes §5, the rest is not this skill's:

- `.spec` `icon=` entry, `datas` entry, and the multi-resolution requirement → **`ui-project`**.
- `iconbitmap` through the `sys._MEIPASS` helper, and `SetCurrentProcessExplicitAppUserModelID` before the root window → **`python-ui`**.
- Confirming all three surfaces (Explorer, title bar, taskbar) show the intended image after packaging → **`ui-project`** verification, and `exe-verify` for capturing the window to look at.
